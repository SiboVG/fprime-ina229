# FT232H bench deployment

The optional POSIX example is a real FPP topology: `Ina229Bench.sensor.spi`
connects to `Ina229Bench.spi.exchange`. Main configures and polls the manager
through generated input ports, then prints CSV. It uses no GDS services or command
dispatcher. Build artifacts include the topology dictionary. Add the usual F Prime
services/patterns in a mission deployment.

The host driver sends full-duplex byte transactions to `bridge.py` over a local
Unix socket. Python owns PyFtdi and the USB device. Neither layer knows INA229
register addresses or unit conversions. Only the manager and device core do.
`library.cmake` does not register the example. Linux/macOS are the intended bench
platforms; the reusable device core has no POSIX or USB dependency.

## Build and run

Use Python 3.11 or newer and the F Prime checkout at the tested revision (including its
recursive submodules).
Create and activate its tool chain as described in
[F Prime integration](fprime.md#f-prime-tool-chain), then build:

```sh
. .venv-fprime/bin/activate
cmake -S examples/Ft232h -B build-ft232h -G Ninja \
  -DFPRIME_FRAMEWORK_PATH=/absolute/path/to/fprime
cmake --build build-ft232h --target Deployment
```

In a separate terminal, install libusb using your host package manager and create
the optional Python environment. Follow [PyFtdi host setup](https://eblot.github.io/pyftdi/installation.html)
for USB access permissions and driver conflicts.

```sh
python3 -m venv .venv-ft232h
. .venv-ft232h/bin/activate
python -m pip install -r examples/Ft232h/requirements.txt
bench_dir=$(mktemp -d /tmp/ina229-bench.XXXXXX)
python examples/Ft232h/bridge.py --socket "$bench_dir/spi.sock" \
  --url ftdi://ftdi:232h/1 --frequency 1000000 --mode 2
```

Use the printed socket path in the deployment terminal:

```sh
build-ft232h/bin/$(uname)/Deployment /tmp/ina229-bench.XXXXXX/spi.sock 0.01 8 10
```

Arguments are socket path, physical shunt resistance in ohms, expected maximum
current in amperes, and sample count (default 10, range 1..100000). Use the actual
shunt and expected range of your circuit. Initialization resets previous device
configuration and accumulated energy/charge. The example selects wide-range,
continuous all-channel acquisition at 50 microseconds per channel without averaging.
It polls readiness at 10 ms with at most 100 attempts, then requests the next row
100 ms later. It exits nonzero on faults and never emits a valid data row for a
failed read. Exiting the example closes SPI but leaves the sensor converting;
power-cycle or use the manager's STOP command in a command-enabled deployment to
shut down conversions. Stopping/restarting the example resets accumulators.

## Wiring and SPI mode

| FT232H | INA229 signal |
| --- | --- |
| ADBUS0 | SCLK |
| ADBUS1 | SDI / MOSI |
| ADBUS2 | SDO / MISO |
| ADBUS3 | CS, active low |
| GND | common ground |

Power the sensor board as specified for that board, use compatible digital voltage
levels, and connect the shunt sense leads and bus input per the TI reference circuit.
Verify board labels, pull-ups and shunt rating before applying a load. Mode 2 is the
working FT232H setting reported by the supplied Python project. It avoids that
project's observed CPHA=1 shifting issue. Other controllers must independently meet
the TI SPI timing diagram; mode 2 is not imposed by the library. CS stays asserted
for the command byte and all data bytes of each exchange. The default clock is 1 MHz;
the CLI bounds requests at 10 MHz, but waveform validation remains required.

## Transport contract

One request is `[length:u8][tx:length bytes]`, with length 1..6. One response is
`[status:u8][rx:length bytes]`; status 0 means a complete transfer, 1 means an error.
Each request maps to one [PyFtdi exchange](https://eblot.github.io/pyftdi/api/spi.html)
with `duplex=True, start=True, stop=True`. Buffer sizes and addresses remain unchanged.
The C++ client has a 1-second deadline per transaction, handles partial socket I/O,
and drops the connection on error, timeout or truncation to discard ambiguous
framing. Reconnect by restarting the deployment. Python accepts one client at a time
and uses a 2-second socket inactivity timeout. USB-library execution can take longer
than the C++ deadline; a late response is never reused by that client.

The socket is mode 0600 in a private directory. The server refuses an existing socket
path rather than deleting it. Stop the server with Ctrl-C; remove the empty temporary
directory afterward. There is no TCP listener, remote-access protocol, or flight
transport implied by this bench example.

## Verification boundary

The C++ transport, Python framing, and generated topology have passed emulated
end-to-end acquisition and injected USB-failure tests. No physical FT232H/INA229
connection was available for this implementation run. Follow the hardware checklist
in [verification](verification.md) before treating the example as hardware-validated.
